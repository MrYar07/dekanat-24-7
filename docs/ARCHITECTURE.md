# Архитектура «Деканат 24/7»

Черновик 0.1 от 05.11.2026. Требования к продукту — в [PRD.md](PRD.md).

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Приложение | Next.js (App Router) + TypeScript | фронт и сервер в одном проекте, серверные компоненты не отдают лишние данные в браузер |
| UI | Tailwind CSS + shadcn/ui, иконки Lucide | быстро, доступно (Radix под капотом), лицензии MIT |
| База | PostgreSQL + Prisma | надёжная реляционная модель, миграции, масштабируется |
| Валидация | Zod | одна схема для форм и API |
| Пароли | argon2id (`@node-rs/argon2`) | современный стандарт хеширования |
| Сессии | своя таблица сессий, случайный токен в cookie `HttpOnly; Secure; SameSite=Lax` | полный контроль, можно отозвать все сессии |
| Живые обновления | Server-Sent Events + PostgreSQL `LISTEN/NOTIFY` | оценка и статус прилетают без перезагрузки; работает и при нескольких экземплярах приложения |
| PDF-справки | `pdf-lib` + шрифт с кириллицей (OFL) + `qrcode` | генерация на сервере |
| Графики | Recharts | простые графики динамики оценок |
| ИИ (P2, отложено) | YandexGPT или GigaChat, вызов только с сервера | доступны из России; ключ в переменной окружения |
| Тесты | Vitest (логика), Playwright (сценарии, мобильный viewport, проверка доступа) | |
| Хостинг | российский VPS, Docker Compose: приложение + PostgreSQL + Caddy (HTTPS) | открывается без VPN, автоматический сертификат |

## Модель данных (первая версия)

```
User ─┬─ StudentProfile (группа, курс, направление, номер зачётки)
      ├─ StaffProfile (роль: TEACHER | DEAN_OFFICE)
      └─ Session

Faculty ─ Program ─ Group ─ StudentProfile
Discipline ─ Course (дисциплина в группе в триместре, преподаватель)
Lesson (пара: Course, время, аудитория, тип) ─ LessonChange (перенос, отмена, причина)
Term (триместр, учебный год)
Checkpoint (срез: Course, номер, срок) ─ CheckpointScore (Checkpoint, StudentProfile, 0–100)
Attendance (Lesson, StudentProfile, был / не был / уважительная причина)
CourseResult (Course, StudentProfile: бонус ≤5, активность, оценка сессии, число пересдач)
AchievementCategory (направление, вид, максимум баллов) ─ Achievement (StudentProfile, Term, вид, подтверждение, статус, начислено)
GradingSettings (веса частей, шкала оценок, порог автомата, штраф пересдачи, коэффициент бонуса, пороги привилегий)
DocumentType (справка или заявление, мгновенная или нет, поля формы)
Request (StudentProfile, DocumentType, данные формы, статус) ─ RequestEvent (история статусов)
IssuedDocument (Request, код проверки, дата, PDF)
Announcement (аудитория: все, курс, группа) ─ Notification (User, тип, ссылка, прочитано)
```

## Расчёт рейтинга

Чистые функции в `lib/grading`, покрыты юнит-тестами, одни и те же на сервере и в калькуляторе «а если…».

Правила и значения по умолчанию — в [GRADING.md](GRADING.md), в коде они лежат в `GradingSettings`.

```
Т (триместр)   = min(100, среднее(выставленные срезы) + бонус)      # бонус ≤ 5
С зачёт        = Т, если Т ≥ 75 (автомат); иначе min(74, оценка)
С экзамен      = оценка
С итог         = max(0, С − 10 × число пересдач)
В (вовлечённ.) = 0,5 × посещаемость% + 0,5 × активность
Д (дисциплина) = 0,40·Т + 0,45·С + 0,15·В
R триместра    = min(100, среднее(Д) + 0,04 · min(100, Σ баллов активности))
Год            = среднее(R без бонуса активности)
```

**Прогноз до сессии:** если С ещё нет, подставляем Т; если нет активности, считаем В по посещаемости. Результат помечается как прогноз.

**Калькулятор** решает уравнение относительно неизвестного балла (следующий срез, экзамен) и проверяет, что ответ в пределах 0–100. Если цель недостижима, честно об этом говорит.

Округление до 0,1 только при показе. Все функции покрыты юнит-тестами, включая граничные случаи: ровно 75, переполнение 100, две пересдачи, нет срезов, нет занятий для посещаемости.

## Безопасность

1. **Доступ к данным только через сервер.** Каждый запрос к базе строится от пользователя из сессии: `where: { studentId: session.studentId }`. ID из адреса никогда не используется без такой проверки. Чужой объект возвращает 404, а не 403, чтобы не подтверждать, что он существует.
2. **Роли проверяются на сервере** в одном месте (`requireRole`), а не скрытием кнопок.
3. **Пароли:** argon2id, ограничение попыток входа по логину и IP.
4. **Сессии:** токен 256 бит, в базе хранится его хеш, срок жизни, выход отзывает сессию.
5. **Секреты:** только в переменных окружения сервера. В клиентский код не попадает ничего, кроме `NEXT_PUBLIC_*`, и туда секреты не кладём.
6. **CSRF:** серверные действия Next.js + `SameSite=Lax` + проверка `Origin` у изменяющих запросов.
7. **Заголовки:** CSP, `X-Content-Type-Options`, `Referrer-Policy`, HSTS.
8. **Проверка справки по QR:** код случайный, 128 бит. Публичная страница показывает только тип документа, дату, статус и маскированное ФИО («Смирнова А. В.»).
9. **ИИ:** модель получает только данные вошедшего студента, подобранные сервером. Ответ ИИ — это намерение (открыть раздел, заполнить форму), а действие выполняет обычный код с теми же проверками доступа.

## Окружения

- **Локально:** `npm run dev` + PostgreSQL. Docker на машине разработчика не установлен, поэтому для разработки берём локальный PostgreSQL или облачную dev-базу (решим на этапе каркаса).
- **Прод:** VPS в AdminVPS (дата-центр в Москве), Ubuntu 24.04, Docker Compose, Caddy с HTTPS, ежедневный бэкап базы. Минимум 2 ГБ RAM; образ приложения собираем не на сервере, а заранее (GitHub Actions или локально), чтобы сборка не упиралась в память VPS.
